# bili-purge

批量取关 UP / 批量清理收藏夹，**用抽样代替硬性天数阈值**。

带一个本地 Web 控制台：扫码登录、预览计划、按每日配额执行、每天自动跑一次。
也可以完全不用界面，直接跑脚本。

```bash
node --test     # 266 项单测，不联网、不碰账号
node demo.js    # 两种标尺的对照
npm run gui     # 打开控制台（默认 http://127.0.0.1:8791）
```

**核心想法**：什么算"新鲜"不该由「60 天内」这种拍脑袋的数字决定。
把关注列表按年龄排序、按比例切成三段，每段保留不同比例，
再在段内按指数权重抽样。于是**规则对任何账号都一样**，
而且**确定性可复现**（同 seed 同结果）——所以你可以先预览，再决定执不执行。

> ⚠️ 它会**真实改动你的 B 站账号**（取关、删收藏）。
> 请先预览、确认名单，再执行。项目按 MIT 发布，风险自负。

需要 Node 20.11+，运行时只有一个依赖（`qrcode`，用于扫码登录）。

## 标尺：不用绝对天数

新鲜度不来自 `60 天内 / 60~365 天 / 大于 365 天` 这类固定阈值，
而是**由数据自身的跨度决定**。时间轴按比例切分：

| 桶 | 时间轴位置 | 保留比例 |
|---|---|---|
| fresh | 0 ~ 30% | 0.95 |
| normal | 30% ~ 70% | 0.50 |
| stale | 70% ~ 100% | 0.30 |

位置怎么算，有两种读法，**它们不等价**，本仓库都实现了：

### `mode: 'quantile'`（默认）——按**项目数**比例切

把列表按年龄排序，位置 = 名次 / (n-1)。每桶恒占固定**人数份额**（30%/40%/30%）。

优点：对离群值免疫，且**恒定可复现你举的例子**——
10 个关注，3 新 / 4 中 / 3 老 → 留 **3 / 2 / 1**，一字不差。

### `mode: 'span'`——按**年龄跨度**比例切

位置 = (age − min) / (max − min)。这是"时间跨度比例"的字面实现。

代价：**一个极老的关注会把标尺整体拉长**。`node demo.js` 在真实的长年账号分布上
跑出来的差异很直观：

```
mode = quantile
  fresh        11   keep 10   1 .. 190
  normal       15   keep  8   250 .. 2560
  stale        11   keep  3   2860 .. 6000

mode = span
  fresh        23   keep 22   1 .. 1780      <-- 把将近 5 年前的关注也算成 fresh
  normal        8   keep  4   2020 .. 4100
  stale         6   keep  2   4400 .. 6000
```

span 模式下 `fresh` 桶吃进了 **1780 天（近 5 年）** 的关注，并被 0.95 的高保留率保护，
整轮只丢 9 个；quantile 模式丢掉 16 个。

**结论：默认用 `quantile`。** `span` 保留作为可切换选项，但它不适合"越老越该走"的直觉。

## 保留下来的数量是确定的，留谁才是随机的

`k = round(n × 保留比例)` 是确定的，只有"留哪 k 个"由种子决定。
所以"留下 2 个左右"实际是**精确留 2 个**，不会飘成 0 个或 4 个。
同一 `seed` 可以复现同一次结果，便于先审阅再执行。

桶内按年龄加权：`P(保留) ∝ exp(-position / tau)`，越老越容易被砍。
实测（10 项、保留一半、2000 次）：

```
item0 (0d)  91.2%   item5 (5d)  42.2%
item1 (1d)  85.8%   item6 (6d)  31.9%
item2 (2d)  77.2%   item7 (7d)  24.3%
item3 (3d)  64.3%   item8 (8d)  17.7%
item4 (4d)  51.5%   item9 (9d)  14.1%
```

## "每轮结束后重置"是自动成立的

权重是**年龄的纯函数**，不累积、不落盘，所以没有状态需要清。

副作用要知道：**连着跑两次，第二次会继续砍**（幸存的还是那么老）。
所以驱动层要加冷却期，或者只允许手动触发。

## 配置

`src/config.js` 里两套预设，因为两者风险不对称：

| | 取关 `UNFOLLOW_PRESET` | 收藏夹 `FAVORITE_PRESET` |
|---|---|---|
| 保留比例 | 0.95 / 0.50 / 0.35 | 0.90 / 0.45 / 0.25 |
| 每轮上限 | 30 | 60 |
| 请求间隔 | 1.5–4s | 0.8–2s |
| 额外 | 保护特别关注 / 互关 | 优先清理失效视频 |

理由：取关**几乎不可逆**，且更容易触发风控；收藏夹删除重新收藏即可，风险低一个量级。

## 接口

```js
import { plan } from './src/sampler.js';

const result = plan(items, config);
// items:  [{ id, ageDays, label? }]        id = mid 或 aid
// result: { keep, drop, buckets, mode, seed }
```

`plan()` 是纯函数：不改动入参，不读时钟，不碰网络。

## 测试覆盖

- 复现 3 / 2 / 1；缩放或平移所有年龄后结果**完全不变**（标尺相对性的核心断言）
- 保留数量确定、留谁随种子变化；同种子可复现；不同种子确实不同
- 权重不累积（连跑两次同种子结果一致）
- 桶内年轻者存活率更高、且总数守恒
- 边界：空列表、单项、年龄全相同（span=0）、keep=0/1、negatives
- 配置校验：桶不递增、末桶不闭合到 1、keep 越界、tau=0 等一律报错
- 投入顺序不被改动；drop 按最老优先排序

期间抓到一个真实 bug：分桶时只判了上界，导致每个桶把更年轻的项也吞了进去
（1000 项时 `normal` 变 700）。已改为半开区间 `[from, to)`，末桶无上界以容纳
恰好在位置 1 的最老项。这个 bug 就是被"大样本按比例切分"那条测试抓出来的。

## 第二步：只读快照（已完成）

`fetch-snapshot.js` **只发 GET 请求**，没有任何写接口，因此跑它不可能改动账号。

```bash
node fetch-snapshot.js --init                # 生成凭据模板（已生成）
node fetch-snapshot.js --check               # 只校验凭据，不联网
node fetch-snapshot.js --whoami              # 确认 cookie 有效
node fetch-snapshot.js --followings          # 拉全部关注，落盘 JSON
node fetch-snapshot.js --folders             # 列出收藏夹
node fetch-snapshot.js --folder <mediaId>    # 拉某个收藏夹
node fetch-snapshot.js --folder <id> --plan  # 顺便打印"将会删除谁"
```

常用开关：`--limit-pages N`（先少量试拉）、`--seed N`、`--mode quantile|span`、
`--out DIR`、`--show N`。

### 凭据

路径：`~/.bili-purge/credentials.json`（已在仓库外，且 `.gitignore` 也挡了一层）。

```json
{ "sessdata": "填这里", "biliJct": "", "mid": null }
```

- **只读只需要 `sessdata`**。`biliJct` 是写操作的 CSRF token，现在不用填。
- 取值：DevTools → Application → Storage → Cookies → `https://www.bilibili.com`
  → 复制 `SESSDATA` 那一行的 **Value 列**（不是整条 cookie 字符串）。
- 也可以走环境变量：`BILI_SESSDATA` / `BILI_JCT` / `BILI_MID`。

### 凭据安全规则（由代码保证，并被测试覆盖）

1. **值永不打印**。`--check` 只显示长度和 `sha256` 前 10 位——
   既能确认"读到的确实是同一个凭据"，又不泄露内容。
2. **值永不写入快照**。`renderPlan` 有一条测试专门断言渲染结果里不含 `raw.sessdata`。
3. 模板只在**不存在**时创建，绝不覆盖你已填好的文件。
4. 配错（JSON 坏了、数组、字段为空）一律**报错退出**，不静默降级。

### 请求安全

- 每次请求之间有随机间隔（默认 1.2–2.6s），不像突发流量。
- B站即使拒绝也返回 HTTP 200，真实状态在 JSON 的 `code` 里，所以客户端会看 body：
  - `-101` 未登录 → **立即失败**，重试无意义
  - `-352` 风控 / `-412` 拦截 / `-509` 太频繁 → 指数退避重试
- 带 `User-Agent` / `Referer` / `Origin`，否则部分接口直接拒。
- 记录请求数与重试数，跑完打印。

### 已知边界

关注列表接口**可能对深翻页设上限**：返回的 `total` 大于实际能翻到的条数。
脚本会把这种情况标成 `complete: false` 并在 `--followings` 里提示，
快照 JSON 里也记了 `reportedTotal` 与 `fetched`，不会假装拿全了。

## 审计：写操作前的最后一道关

```bash
node audit-snapshot.js --cap=365 --dump=review.txt
```

读快照、不联网，输出：年龄分布分位数、各桶实际年龄范围、保护名单是否泄露、
以及**不同 cap 对结果的影响对照表**，并把完整名单写成文件供你逐条核对。

### capDays：给"新鲜"加一个绝对上限

纯相对标尺有个后果：它保护的是**按名次**最年轻的 30%。在一个本身就很老的账号上，
这可能意味着保护了一批两三年前的关注——实测这个账号的 `fresh` 桶一直延伸到 **798 天（2.2 年）**。

所以每个桶可以有选择地加 `capDays`：超过这个天数的条目会被**下推到下一个桶**，
于是"新鲜"同时具备绝对含义。末桶的 cap 会被忽略，保证任何条目都有归属。

对照表（真实数据，1760 个关注）：

| fresh cap | fresh 桶条目 | 实际年龄范围 | 保留 | 取关 | 取关占比 |
|---|---|---|---|---|---|
| 90d | 40 | 6 .. 90 | 819 | 941 | 53.5% |
| 180d | 103 | 6 .. 178 | 848 | 912 | 51.8% |
| **365d** | 215 | 6 .. 364 | 898 | 862 | **49.0%** |
| 730d | 452 | 6 .. 730 | 1004 | 756 | 43.0% |
| none（纯相对） | 528 | 6 .. 798 | 1039 | 721 | 41.0% |

配置写法：

```js
buckets: [
  { name: 'fresh',  to: 0.3, keep: 0.95, capDays: 365 },
  { name: 'normal', to: 0.7, keep: 0.5 },
  { name: 'stale',  to: 1.0, keep: 0.35 },
]
```

### 保护名单（真正生效）

`followingsProtection()` 是传给抽样器的谓词，`特别关注` / `互相关注` 一律不取关。
实测这个账号：111 个受保护，其中 **59 个在没有这层保护时会被取关**——
保护不是装饰，它确实在挡刀。

受保护条目**占用**本桶配额，而不是额外叠加，因此保护不会让"取关总量"失真。

## 第 5 步：收藏夹批量删除

```bash
node fetch-snapshot.js --folders                    # 找到 media id
node fetch-snapshot.js --folder 60971020            # 抓该收藏夹的快照
node purge-favorites.js --cap=365                   # 预览，什么都不会发生
node purge-favorites.js --folder=60971020 --cap=365 --limit=20 --execute --confirm=XXXXXXXX
```

安全模型和取关完全一致（默认 dry run、令牌只能确认打印过的那份计划、
单轮/单日上限、审计日志、遇风控码中止），但**配额更宽**：

| 参数 | 取关 | 收藏夹 | 为什么不同 |
|---|---|---|---|
| 单轮上限 | 30 | 100 | |
| 每日上限 | 150 | 400 | |
| 请求间隔 | 8–20s | 2.5–6s | 收藏夹删除**可撤销** |
| 每请求 | 1 个 | 20 个（`batch-del`） | 接口支持批处理 |

风险不对称是刻意的：取关几乎不可逆、且更容易触发风控，所以保守；
收藏夹删除有 `restore-favorites.js` 兜底，所以可以更激进。

### 顺序：失效视频优先

`buildFavoriteRun` 默认把**已失效**的条目排在前面先删
（`deadFirst`）。它们已经没有任何价值，删掉不可能后悔。

### 撤销

```bash
node restore-favorites.js --log=logs/favorites-xxx.jsonl            # 预览
node restore-favorites.js --log=logs/favorites-xxx.jsonl --execute --confirm=XXXXXXXX
```

走 `/x/v3/fav/resource/deal` 把 `rid` 重新加回 `add_media_ids`。

**两个诚实的限制：**

1. **恢复不了原始收藏时间**。恢复后的条目在后续标尺里会显得"刚收藏"。
2. **失败的批次不会自动恢复**。`batch-del` 不逐条报告结果，
   一批失败时无法知道其中哪几条其实已经删掉了。这类条目按失败记录，
   不盲目恢复（否则可能把还在的条目重复添加）。日志里有 `ok: false` 可查。

另外，**已经失效的视频无法恢复**——视频本身被 UP 删了，收藏夹里只是个占位符。
这类条目删掉是安全的，只是也回不来。

### 部分快照会被警告

如果快照是用 `--limit-pages` 抓的，脚本会打印警告。**不要基于部分快照执行删除**：
它只覆盖收藏夹的一部分，标尺会把这一部分当成全体，分位数会算错。

实测这个默认收藏夹还暴露了另一个来源：API 报 `media_count = 3277`，
但翻页在 `has_more: false` 时停下，只抓到 **3228** 条，**少 49 条**。
深翻页本身不稳定（条目会在页之间移动）。所以脚本现在会**从数量推导**是否完整，
不依赖快照里的 `complete` 字段——旧快照也能被正确判断：

```
WARNING: snapshot is INCOMPLETE -- 3228 entries but the API reported 3277.
```

### `attr` 不是失效标志（一个被抓到的误判）

原先的失效判定把 `attr !== 0` 当作"已失效"。**这是错的。**

实测数据里 `attr` 非 0 的 28 条全部有**正常标题 + 有效 bvid**：

| attr | 实际含义（推断） | 例子 |
|---|---|---|
| 16 | 互动视频 | 《你被困在2025年10月25日（全新9个循环）》 |
| 2 | 官方/精选内容 | 胡彦斌《红颜》、洛天依《又见·明月光》、总台春晚、上甘岭修复版 |

它们全是活着的视频。因为 `deadFirst` 排序，这 28 条会被**排在最前面优先删除**，
还被标成 `[dead]` 让你以为删了不心疼。

（想用 `/x/web-interface/view` 逐个核实，但该接口要求 WBI 签名，直接返回 412，
所以这里的结论来自标题与 bvid 的可靠性，不是接口确认。）

修法有两条，都做了：

1. **`invalidReason` 不再看 `attr`**，只认真正的信号：占位标题（`已失效视频`）、缺 bvid
2. **判定改为重新计算，而不是读快照里缓存的 `invalid` 布尔值**——
   快照是某个时刻的判定结果，检测逻辑改了它不会跟着变。重新计算意味着
   **旧快照不可能把活着的条目排进删除队列**。

输出也从 `[dead]` 改成打印**具体理由**，你可以自己判断：

```
2132d   98189285  已失效视频  [placeholder title "已失效视频"]
```

## 第 4 步：执行（唯一会改动账号的部分）

```bash
node unfollow.js --cap=365 --limit=5              # 预览，什么都不会发生
node unfollow.js --cap=365 --limit=5 --execute --confirm=B88B4B9C
```

**默认永远是 dry run。** `--execute` 必须配一个 `--confirm` 令牌，而令牌是对
"本次实际动作列表 + 标尺设置 + seed" 做 sha256 取前 8 位得到的。所以：

- 改了 cap、seed、白名单或 `--limit`，令牌就变——**抄上一份计划的令牌执行不了这一份**
- 你必须先看过那份计划，才能拿到那个令牌

### 内置的安全约束

| 约束 | 说明 |
|---|---|
| 特别关注 / 互相关注 | 谓词层直接拦掉，永不进入动作列表 |
| `--keep=<mid,...>` | 白名单，同样永不进入 |
| `maxPerRun` | 单次上限（取关 30，收藏夹 60） |
| 请求间隔 | 取关 1.5–4s 随机，比任何只读操作都慢 |
| 顺序 | **最老的先动**，试跑小批量时先碰最不心疼的那批 |
| 风控响应 | `-352/-412/-509/-799` **立即中止整轮**，绝不加大重试力度 |
| 审计日志 | 每次尝试追加一行 JSONL 到 `logs/unfollow-*.jsonl` |

风控码在 `src/http.js` 里只定义一次（`RISK_CONTROL_CODES`），读路径拿它做退避重试，
写路径拿它做中止——两条路径不可能对"什么算被拒绝"产生分歧。

### 写路径的重试策略

**网络失败会重试**（这两个接口都是幂等的：取关两次、删除两次，结果一样），
**但风控拒绝和 HTTP 错误不重试**——被拒绝时应该停下来让人判断，
而不是加大力度，那正是账号被锁的方式。

### 一次能删多少？——风控与配额

**先说清楚：B站不公开任何阈值，没人能给你一个"保证安全"的数字。**
下面的默认值是保守估计，不是官方上限。

可能发生什么（按可能性排序）：

| 后果 | 可能性 | 说明 |
|---|---|---|
| `-352` / `-509` 临时限流 | 高 | 取关/关注被暂时拒绝，通常几小时到一两天 |
| `-412` 请求被拦截 | 中 | 操作被拦，可能升级为更长的限制 |
| 账号被限制 | 低 | 波及更多功能 |
| 永久封号 | 很低 | 一般针对垃圾内容/违规行为，不是"取关自己的关注" |

真正触发识别的**不是总数，而是行为模式**：

1. **速率**——一次性连发几百个请求
2. **间隔过于规整**——机械的等间隔比总数更显眼
3. **没有其他活动**——真人刷 B站 会夹杂浏览、点赞、看视频

所以本项目的默认节奏：

| 参数 | 默认值 | 依据 |
|---|---|---|
| 请求间隔 | **8–20s 随机** | 同类维护中的工具用 5–20s 并称"基本不会触发风控"，这里取慢的一端 |
| 单轮上限 | **30** | 一次坐下来跑完的量 |
| 每日上限 | **150** | 主要防线。862 个约需 6 天 |

每日配额**从审计日志重新推导**，不存计数器，因此永远不会和真实发生的事漂移：

```
daily quota: 5/150 used today -- 145 left
```

**最重要的一条规则：一旦出现 `-352`，当天就停，而不是等五分钟继续。**
脚本已经会自动中止整轮（见下），但不要当天再手动重试。

日期边界用**本地时区**，不是 UTC——凌晨 1 点跑的算"今天"。

### 执行后必须核实

`code: 0` 只代表"B站接受了这次调用"，**不等于状态真的变了**。用一次请求核实：

```bash
node fetch-snapshot.js --whoami     # following 1755   followers 594
```

（`/x/web-interface/nav` 并不返回关注数——实测它的字段里没有 `following`/`follower`。
所以走 `/x/relation/stat`，仍然只要一次请求。）

### 重复取关是安全的（实测）

对**已经取关**的 mid 再次 `act=2`，接口返回 `code: 0`（幂等空操作），不报错也不触发风控。
所以旧快照不会让后续轮次失败。即便如此，每轮之前重拉一次快照仍是好习惯：

```bash
node fetch-snapshot.js --followings
```

## 控制台（GUI）

```bash
node gui.js            # http://127.0.0.1:8791
node gui.js --port=9000
```

零依赖（`qrcode` 用于扫码登录，见下）：Node 自带的 `http` 加上一个 HTML 页面。
**只监听 `127.0.0.1`。** 界面上能改的东西和命令行参数是同一套：
每日上限、单轮上限、`fresh` 绝对上限、白名单 UP / 白名单视频、收藏夹、以及凭据。

### 扫码登录（推荐）

点「扫码登录」，用手机 B站 App 扫一下，和在新设备上登录完全一样。
**全程不碰 Cookie**，凭据直接写进 `~/.bili-purge/credentials.json`。

流程就是 B站 自己的那套：

```
GET  /x/passport-login/web/qrcode/generate   -> { url, qrcode_key }
GET  /x/passport-login/web/qrcode/poll       -> 86101 未扫码 / 86090 已扫描
                                                86038 过期   / 0 成功
```

成功那次响应通过 `Set-Cookie` 带回 `SESSDATA` / `bili_jct` / `DedeUserID`，
`src/qrlogin.js` 把它们取出来；万一 Cookie 被中间层剥掉，还会退回去读
响应里跨域 URL 的查询参数（双重兜底）。

**登录 URL 不会交给页面**：浏览器只拿到一张二维码图片（服务端渲染的 SVG），
拿不到那个可以直接打开的链接。已用测试断言这一点。

代价：为了画二维码引入了 `qrcode`（MIT，29 个包含传递依赖）。
手写 QR 编码器（Reed-Solomon + 掩码 + 对齐图案，约 300 行）在没法用手机
验证的情况下出错风险太高——画错了就是扫不出来，所以没有硬上。

### 不想扫码：整段粘贴

**F12 → Network → 任意请求 → 右键 `Copy as cURL` → 整段粘进控制台。**

解析器接受这几种形状，都会自己挑出需要的那两个值：

| 粘贴内容 | 说明 |
|---|---|
| `SESSDATA=...; bili_jct=...; ...` | 裸 Cookie 串 |
| `Cookie: SESSDATA=...` | 带前缀的行 |
| `curl 'https://...' -H 'Cookie: ...'` | Copy as cURL（最省事） |
| `{"sessdata":"...","bili_jct":"..."}` | JSON |

**多余的 Cookie 会被丢弃**（`buvid3`、`b_nut` 之类不会被保存），
控制台也**从不回显**这两个值——只显示长度和 sha256 前 10 位。

### 为什么"复制网址"拿不到 Cookie

这是 B站 登录态的设计，不是实现问题：

- `SESSDATA` 和 `bili_jct` 都是 **HttpOnly** Cookie。`document.cookie` 读不到它们，
  任何网页脚本都读不到——这正是 HttpOnly 存在的意义（防 XSS 偷登录态）。
- Cookie 是 HTTP **请求头**，**永远不出现在网址里**。复制地址栏得到的是一个干净的 URL。
  实测：`https://www.bilibili.com/` 的参数列表是空的。
- 如果网址里真能带出登录态，那任何贴链接的场合都会泄露账号。

所以只有两条路：**扫码**，或者**从 Cookie 里取**。

### 它是怎么防止别的网页乱点的

控制台只监听 `127.0.0.1`，但**任何网站的页面都能向本机 POST**（读不到响应，
但请求会到）。所以每次启动都会生成一个随机令牌，页面里带着它，
所有 `/api/*` 都必须带上自定义头 `x-bili-purge-token`。

自定义头会触发 CORS 预检，而本服务**从不返回任何 CORS 头**，
于是跨站请求在预检阶段就被浏览器挡掉。测试里断言了无令牌/错令牌一律 403。

### 界面：两栏、双计划、一次执行两个

左边 1/2/3（凭据、取关、收藏夹清理），右边 4/5/6（预览与执行、每日任务、历史）。
窄屏自动叠成一列。

**两个计划可以同时预览**。预览取关之后再预览收藏夹，取关那张卡片不会被覆盖——
每张卡片带自己的令牌，两边都预览过就会出现一个「两个都执行」按钮。

这不是放松了约束：服务端每次执行都会**重新推导计划再比对令牌**，
所以哪个计划的令牌在你查看期间失效了，那一个会明确报错，
而不是拿你看到的旧计划去动手。

执行按钮会显示**已经跑了多少秒**。取关每次间隔 8–20 秒，3 项就要将近一分钟，
没有这个反馈很容易以为卡死了。（早先它确实会永远停在「执行中…」——
执行成功后只刷新了数据区、没重画预览区，按钮就再也没恢复。）

### 背景图

顶栏右侧有三个控件：**背景开关**（记在浏览器本地）、**上传背景**、**恢复默认**。

默认背景是**为这个工具画的原创图**（`gui/assets/backdrop.svg`）：
B 站品牌粉 `#FB7299` 和蓝 `#23ADE5` 的辉光，加上首页最有辨识度的两样东西——
**视频卡片网格**和**弹幕**。它不是 B 站的素材，所以可以随项目一起分发。

点「上传背景」选一张图，会先弹出一个裁剪框：**在框里拖动图片选位置，
用滑块决定往里放大多少**。框是 16:9 的，所见即所得——框住哪一块，背景就是哪一块。
点「用这一块」才会上传，点「取消」什么都不发生。

裁剪在浏览器里做：先在 canvas 上按你选的框裁出来，再编码成 1920×1080 的

服务端收到的是裁好的成品。缩放时以框心为基准，所以放大不会把选好的位置甩掉；
拖动到头就停住，不会露出空白边。

图片存成一个文件：

```

gui/assets/backdrop.svg       # 内置的，兜底
```

改名成 `.png` 的 HTML 会被拒（否则它就能以本页的源被回放）。SVG 不在白名单里，
因为它可以携带脚本。解码后上限 8 MB。

B 站官方的美术素材是他们自己的版权资产，你可以自己放进来用，但本项目不打包分发它们。

静态资源只开放 `/assets/` 一个目录，文件名经 `path.basename()` 收敛，
`/assets/../gui.js` 这类路径一律 404（有测试）。

## 每日自动运行

```bash
node daily.js           # 无人值守跑一轮（刷新快照 → 按配额执行）
node daily.js --dry     # 只演算，不写
node daily.js --only=unfollow
```

也可以直接在控制台点「安装每日任务」。

### 它跑**一轮**，不会跑到上限

```
本轮数量 = min(单轮上限 perRun, 当日剩余配额)
```

跑完这一轮就结束，**不会循环**直到把每日上限用满。
单轮 3 / 每日 15 就是每天自动取关 **3** 个，不是 15 个。

每日上限只是**天花板**：它保证手动跑的几次加上自动跑的那次合起来不超过 15，
而不是"每天必须删满 15"。想要每天跑满，把单轮上限设成等于每日上限即可。

### 它和手动的 CLI 有什么不同

CLI 是人盯着的，所以可以停下来要确认令牌。定时任务**没人在场**，
所以配额和设置文件**就是**授权——**安装任务这个动作本身就是授权**，
这也是它需要你明确点一下、而且能一键删掉的原因。

### 每次都会先重抓快照

计划依赖快照。拿一个月前的快照去执行，标尺排的是**一批已经不存在的人**。
所以 `daily.js` 每次都先重新抓一遍，再算计划，再执行。

### 三个真实限制

1. **Cookie 会过期**（通常约一个月）。过期后 `daily.js` 会**明确报错**，
   不会静默什么都不做：

   ```
   cannot run: could not authenticate (-101: 账号未登录).
     This usually means SESSDATA has expired. Paste fresh cookies in the GUI.
   ```

   但它不会自己恢复——你还是得回来重新粘一次凭据。

2. **退出码是有意义的**，任务计划程序会记录：

   | 退出码 | 含义 |
   |---|---|
   | 0 | 跑完了，或者今天没有该做的事 |
   | 1 | 跑不起来（设置坏了 / 凭据缺失或过期 / 抓取失败） |
   | 2 | **被风控中止**——账号正在被限流，今天不要再试 |

3. **它默认关着。** `settings.json` 里 `favorites.enabled` 和 `schedule.enabled`
   都只认**显式的 `true`**。`1`、`"true"`、`"yes"` 一律当假——
   删收藏夹和无人值守是风险更高的动作，**模糊输入必须失败关闭**。

### 它是怎么被调度的

Windows 任务计划程序，任务名 `BiliPurgeDaily`：

```powershell
schtasks /Query /TN BiliPurgeDaily /FO CSV /V
```

卸载就是 `schtasks /Delete`，控制台上点一下即可。

> 实现细节：`schtasks` 的输出是本地化的，中文 Windows 上是 GBK。
> 所以代码**不按标签名匹配**（`Next Run Time` 在中文系统上根本不存在），
> 而是用 `/FO CSV /V` **按列位置**读，并用 `TextDecoder('gbk')` 解码。
> 实测解析结果：`nextRunTime: "2026/10/9 3:30:00"`、`status: "就绪"`。

    而不是换行；存回去时按空白拆分，字面 `\n` 不是空白，两条 ID 就变成了一条

    代价是真实的：`共青团中央`(20165629) 和 `指法芬芳张大仙`(1935882)
    ——恰好是关注最久、排在最前面的两条——被取关了。
    已用 `refollow.js --limit=2` 从日志恢复，并从服务端确认 `attribute=2`（已关注）。

    现在 `idList` 会按**空白、逗号、分号，以及字面 `\n`** 一起拆，
    所以已经坏掉的文件在读取时就会自愈；单个字符串（而非数组）也不再被丢掉
    ——丢掉等于白名单为空，那是往"删得更多"的方向失败。

第 2、3、4 条都集中修在 `daysBetween`——
**无法解析的时间戳一律当作"最新"**，因为本项目是删东西的，日期不明的条目必须被保护，
而不是被当成"很老"清掉。

## ⚠️ 别用 PowerShell 改这个仓库里的文件

中文 Windows 上，PowerShell 的 `Get-Content` / `Set-Content` 默认走 **ANSI 代码页（GBK）**，
而仓库里的文件都是 **UTF-8**。用它们改一次，中文就永久损坏：

```powershell
# 这一行会毁掉 README.md
(Get-Content README.md -Raw) -replace 'a','b' | Set-Content README.md
```

原因是读的时候把 UTF-8 字节按 GBK 两两配对，**每个 3 字节汉字的最后一个字节
如果后面跟的是 ASCII，就会配对失败被替换成 `?`**——一次 500 多个字符。

这个坑真的踩过：README 被上述命令毁掉，最后是从 DSH 的会话记录里
把历次 `write`/`edit` 重放出来才恢复的（记录是 zstd 压缩的 JSONL）。

**安全做法**：用编辑器或本仓库的 `edit` 工具改文件；
必须用命令行时，走 Node：

```powershell
node -e "const fs=require('fs');let t=fs.readFileSync('README.md','utf8');t=t.replace('a','b');fs.writeFileSync('README.md',t)"
```

```
fetched 3209 entries from "默认收藏夹" (api reported 3,258)
  WARNING: 49 entr(ies) short of the reported count.
  flagged as dead: 205
    205 x placeholder title "已失效视频"
```

两点结论：

1. **缺口又是恰好 49 条**（3228/3277 和 3209/3258 都是 49）。

2. **205 条失效全部是占位标题，一条都不是 `attr` 误判**——

### 顺带抓到的 bug（第 9 条）

dry run 最后打印的执行命令**自己跑不起来**：

```
node purge-favorites.js --folder=60971020 ... --execute   # no snapshot for folder 60971020
```

明明有 `fav-60971020-*.json`。原因是快照里的 `mediaId` 是**字符串**
（`"60971020"`，来自命令行），而过滤用的是 `=== Number(...)`，严格比较
字符串和数字永远不等。所以 `--folder=` **从来没有匹配成功过**，
只有省略 `--folder`（改用最新的快照）才能跑。

修成按字符串比较，并补了 8 个 `pickSnapshot` 的回归测试。
